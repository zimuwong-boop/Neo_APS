# Neo APS 定制化排产展示系统文档

版本：1.0｜日期：2026-10-09｜阶段：展示系统业务闭环已实现，调味品演示数据已准备；最终实施、测试及部署记录见12～14。

部署约定：开发时在项目根目录创建 `.venv`；本机部署为单个 Docker 容器，包含 Vue 构建产物、Django 和 PostgreSQL。详见 [09 开发与部署计划](09-development-deployment.md)。

本次补充已明确：**跨订单合并生产是首版核心功能，订单采用简单五级优先级。** 相同产品和制造版本的需求合并，生产任务取最高来源等级，报工按等级依次回分到需求；详见 [跨订单排产规则与算例](04-scheduling.md)。原 v0.1 的“不跨单合并”假设已撤销。

目标技术栈：Django + Vue + PostgreSQL。一个用户拥有全部权限，完成销售单、生产单 CRUD，以及多级 BOM 驱动的排产建议、人工调整、生产进度反馈闭环。

## 核心设计决策

1. 物料共用 `Item` 主数据，以 `FINISHED / SEMI / RAW` 区分三类；每类都有独立的 `traceability_info` 溯源字段。
2. BOM 用邻接关系保存，业务层级不限；必须检测循环。物料可被多个 BOM 引用，不能当作单一树保存。
3. 成品只能位于 BOM 根部；半成品可独立销售、独立生产，也可作为组件；原料只作为叶子。
4. 排产结果是建议序列与依赖关系，不承诺设备产能或精确完工时间。
5. 建议与已发布生产单分开存储；发布时冻结 BOM 快照、锁定销售需求，避免重复安排。
6. 销售需求按路径展开后跨订单合并兼容任务，保留来源分配。生产单与销售行通过分配表关联；销售进度只统计 SALE 用途的已回分数量，组件用途不重复计数。
7. 优先级为 1～5，1 最高，3 默认。合并任务取最高来源等级，前置制造依赖优先于顺序；部分完工量按冻结的来源等级依次分配。
8. 默认每 2 秒轮询刷新，正常演示环境以报工提交后 3 秒内更新为目标；这是近实时展示口径，不是设备级实时采集。

## 待业务核对的默认假设

五级制和跨订单合并已由用户明确。下表区分这些已明确要求与为形成计划而选定的默认细节；数字方向、合并批次边界、回分及进度刷新规则仍可在开发前核对调整。

| 编号 | 默认值 | 改变后的影响 |
| --- | --- | --- |
| A01 | 不扣减库存，不做采购、齐套校验；只展示原料需求 | 引入库存需增加库存台账、预留与净需求算法 |
| A02 | 五级制已由用户明确；数字方向采用 1 最高、3 默认，同级按交期、创建时间、ID 排序 | 不引入权重评分；排序细节仍可调整 |
| A03 | 每 2 秒轮询；正常网络下 3 秒内可见 | 如果需要服务端推送，改用 SSE/WebSocket 并增加部署与重连测试 |
| A04 | 跨单合并已明确；默认合并本次方案兼容需求，任务取最高等级、产量按等级回分，不自动追加已发布批次 | 已增加需求分配与报工回分表；拆批或在制追加属于后续扩展 |
| A05 | 子生产单全部完成后，父单才允许开工 | 如允许边产边装，需引入子件消耗与可用量核算 |
| A06 | 所有半成品自制；数量支持 6 位小数，无单位换算、损耗、良率与返工 | 采购半成品、整数包装和损耗会改变展开公式 |
| A07 | 每个可制造物料只允许一个当前生效 BOM；已发布版本不可修改 | 并行多工艺需要销售行或生产单选择工艺版本 |
| A08 | 展示生产完成，不处理发货和财务；报工由用户手工填写 | 接设备、仓储或物流需要新增集成协议 |
